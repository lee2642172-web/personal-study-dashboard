# 각 기기에서 기록하면 자동으로 반영됩니다

같은 Supabase 프로젝트·같은 계정으로 로그인하면 PC·iPad·휴대폰에서 한 학습 기록, 할 일, 과업 작업, 일정, 목표와 진도를 자동으로 합칩니다. 기기 사본을 고르거나 온라인 기록 전체를 덮어쓰는 절차는 없습니다.

이미 연결했다면 **각 기기의 대시보드를 한 번 새로고침**하면 됩니다. 기존의 복구 초안과 로그인 전 기록도 자동 병합에 포함하며, 원본과 병합 전 사본은 기기에 보관합니다. Supabase SQL 설정을 다시 실행할 필요는 없습니다.

## 처음 한 번 연결

1. [Supabase](https://supabase.com/dashboard)에 로그인하고 프로젝트를 만듭니다. 무료 플랜을 선택할 수 있습니다. DB 비밀번호는 앱에 입력하지 않습니다.
2. 앱 오른쪽 위 **온라인 저장 연결하기 → 저장소 설정문 복사**를 누르고 프로젝트의 **SQL Editor → New query**에서 실행합니다. 원본은 [setup.sql](../supabase/setup.sql)입니다.
3. **Authentication → URL Configuration**의 Site URL과 Redirect URLs에 실제 대시보드 주소를 등록합니다. Email 로그인도 활성화합니다.
4. 프로젝트의 **Data API**에서 URL을 복사합니다. 끝에 `/rest/v1/`이 붙어 있다면 빼고 `https://프로젝트주소.supabase.co`까지만 앱의 **Project URL**에 입력합니다.
5. **API Keys**의 **Publishable key**를 앱에 입력하고 연결 설정을 저장합니다. 기존 `anon public` 키도 지원합니다. `service_role`, `sb_secret_…` 및 DB 비밀번호는 입력하지 않습니다.
6. 처음 계정 확인은 이메일 링크로 로그인합니다. 이미 로그인된 기기가 있다면 아래의 비밀번호 로그인도 사용할 수 있습니다.
7. 다른 기기에도 같은 URL·공개 키를 넣고 **같은 이메일 계정**으로 로그인합니다. 각 기기의 기존 기록이 자동으로 합쳐집니다.

Vercel 환경변수 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`를 설정해 다시 배포하면 각 기기에서 연결값을 입력하는 단계는 생략할 수 있습니다. `.env.example`을 참고하세요. 이 두 값은 브라우저에 공개되는 값입니다.

## 이메일 발송 한도와 비밀번호 로그인

Android Chrome도 지원합니다. PC·iPad·휴대폰의 연속 메일 요청에는 Supabase의 재요청 간격·발송 한도가 적용됩니다. 앱은 발송 한도, 허용되지 않은 수신자, 잘못된 키, 네트워크 오류 등을 구분해서 표시하며, 메일 요청 성공 후에는 60초 동안 재요청을 막습니다. 이 대기는 서버의 시간별 메일 한도를 해제하는 기능은 아닙니다.

메일 없이 같은 계정으로 로그인하려면 다음처럼 합니다.

1. 로그인된 PC·iPad에서 상단 온라인 저장 상태를 누릅니다.
2. **비밀번호 설정·변경**에서 8자 이상 비밀번호와 확인 입력을 넣고 **비밀번호 저장**을 누릅니다.
3. 휴대폰에서는 **비밀번호 로그인**을 선택하고 같은 이메일·비밀번호로 로그인합니다. 인증 메일은 요청하지 않습니다.

현재 계정의 Supabase Auth 비밀번호만 설정하므로 사용자 ID·학습 기록은 바뀌지 않습니다. 앱의 학습 데이터나 기기 캐시에 비밀번호를 보관하지 않습니다. 프로젝트 보안 정책에 따라 최근 로그인 확인이 필요한 경우 메일 한도가 회복된 후 재로그인이 필요할 수 있습니다.

## 자동 동기화 동작

- 변경은 먼저 해당 기기에 보관하고 약 0.7초 후 온라인에 저장합니다. 다른 기기의 변경은 화면 복귀·재연결 시 또는 화면이 열린 동안 약 3초마다 확인합니다. 조용한 상태에서는 작은 버전 번호만 조회하고 바뀐 경우에만 전체 문서를 받습니다.
- 인터넷이 끊겨도 기록하고 새로고침할 수 있습니다. 연결이 돌아오면 대기 중인 변경과 다른 기기의 변경을 자동으로 합칩니다. 브라우저가 닫혔거나 기기가 절전 상태이면 다음에 화면을 열 때 반영될 수 있습니다.
- 학습 기록·작업 이력·할 일·일정 등은 각 ID로 합칩니다. 같은 ID를 반복 수신해도 복제하지 않습니다. 서로 다른 실제 세션은 각각 유지합니다.
- 서로 다른 항목이나 같은 항목의 다른 필드는 함께 보존합니다. 같은 필드를 동시에 수정하면 논리 수정 순서와 기기 ID로 한 값에 일관되게 수렴합니다. 사용자가 충돌 사본을 선택할 필요는 없습니다.
- 삭제는 삭제 표시도 동기화합니다. 오래된 기기의 사본이나 취소와 겹친 수정이 삭제된 기록을 다시 만들지 못하도록 합니다. 완료 취소·시간 수정은 통계에도 반영됩니다.
- Day별 완료 기록을 합친 뒤 다음 미완료 Day를 재계산합니다. 회독별 학습 위치는 별도로 유지하고, 동시에 추가한 회독도 보존합니다. 신규 Day 범위는 더 큰 등록 범위를 유지합니다.
- 실제 학습일·분·완료 기록 자체는 사용자가 입력한 그대로입니다. 동기화용 수정 순서는 학습 날짜나 학습시간으로 집계하지 않습니다.
- 기기 저장 실패·손상된 데이터·네트워크 오류는 온라인 저장 완료라고 표시하지 않습니다. 원본을 보존하고 재연결 또는 저장 공간 확보 후 이어서 처리합니다.

## 기존 데이터와 복구 사본

로그인 전 원본 키 `personal-study-dashboard:v1`과 이전 연결·교체 백업은 그대로 보존합니다. 계정별 캐시는 프로젝트·사용자별 키로 분리합니다. 처음 자동 병합하기 전에 **기기 기록·온라인 기록·별도 로그인 전 원본**을 추가로 보관하며 이 사본은 일반 백업 4개가 교체되어도 유지합니다.

이전 버전의 **복구 초안도 자동 병합에 포함**합니다. 예전 수정 시각이 없는 동일 필드의 차이는 정확한 실제 수정 순서를 복원할 수 없으므로, 최초 이전 시 복구된 기기 값·로그인 전 값·기존 온라인 값의 우선순위를 사용합니다. 서로 다른 ID의 기록은 모두 보존하며 이전 원본도 남깁니다. 이후의 수정·삭제는 항목별 변경 정보로 처리합니다.

상단 설정의 **기록 백업·복구**에서 사본의 최근 실제 활동일·기록 수·상세 기록을 확인하고 JSON으로 내려받을 수 있습니다. **이 사본의 기록을 현재 기록에 합치기**는 현재 기록 전체를 교체하지 않고 사본의 변경 정보를 합쳐 자동 저장합니다. 이미 삭제된 ID를 가진 오래된 사본은 삭제를 취소하지 않습니다. 외부 JSON 파일 업로드 복원과 서버 전체 버전 이력 조회는 제공하지 않습니다.

최초 기기 원본은 처음 연결한 계정에 연결하고, 계정이나 프로젝트를 바꿨다고 다른 계정으로 자동 업로드하지 않습니다. 복구 화면도 현재 계정의 사본만 열거합니다. 로그아웃해도 해당 계정의 기기 캐시는 남습니다. 공용 기기에서는 로그아웃 후 사이트 데이터도 삭제합니다.

## 저장 프로토콜과 검증

기존 `dashboard_snapshots`와 버전 검사 RPC를 그대로 사용합니다. `DashboardData.syncState`에는 기준 데이터와 ID/필드별 변경 순서·삭제 표시를 저장합니다. 서버 버전이 경쟁하면 최신 변경과 합쳐 자동 재시도합니다. 응답을 기다리는 동안 생긴 추가 편집도 다음 저장에 포함합니다. JSONB의 속성 순서가 바뀌어도 같은 문서로 비교하며, 구버전 탭의 변경도 서버 저장 시각을 기준으로 편입합니다.

RLS는 로그인한 본인의 행만 읽게 하고 직접 쓰기는 막습니다. 쓰기 RPC는 `auth.uid()`와 기대 버전을 검사합니다. 새 SQL이나 새 비밀 키는 필요하지 않습니다.

테스트는 세 기기의 동시 추가, 같은 필드와 다른 필드 수정, 오프라인·새로고침·재연결, CAS 경쟁, 업로드 중 편집, 취소·삭제 재등장 방지, 작업 이력과 통계, 회독·Day 범위, 복구 초안의 자동 이전, 기기 원본 보존과 계정 분리를 확인합니다. 브라우저 테스트는 모의 Supabase API와 별도 PC·iPad·휴대폰 세션을 사용합니다. 실제 사용자 기기의 저장소와 사설 프로젝트를 이 환경에서 직접 조회할 수는 없습니다.
