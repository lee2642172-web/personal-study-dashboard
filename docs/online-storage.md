# PC·iPad에서 같은 기록 사용하기

앱 오른쪽 위 **온라인 저장 연결하기**에서 설정합니다. 이 연결을 마치기 전에는 기존처럼 기기에 저장되며, 화면에서도 온라인 저장 완료라고 표시하지 않습니다.

## 처음 한 번

1. [Supabase](https://supabase.com/dashboard)에서 로그인하고 새 프로젝트를 만듭니다. 제공되는 무료 플랜을 선택할 수 있습니다. 프로젝트 생성 시 정하는 DB 비밀번호는 앱에 입력하지 않습니다.
2. 앱의 **저장소 설정문 복사**를 누르고 Supabase 프로젝트의 **SQL Editor → New query**에 붙여 넣어 실행합니다. 원본은 [setup.sql](../supabase/setup.sql)입니다.
3. Supabase **Authentication → URL Configuration**에서 **Site URL**을 실제 Vercel 대시보드 주소로 설정하고 같은 주소를 **Redirect URLs**에도 등록합니다. 미리보기 주소도 사용한다면 별도로 등록합니다. Email 로그인은 활성화되어 있어야 합니다.
4. 프로젝트의 **Connect** 또는 **Settings → API Keys**에서 **Project URL**과 **Publishable key**를 확인하여 앱에 입력합니다. 기존 프로젝트는 `anon public` 키도 지원합니다. `service_role`, `sb_secret_…` 키와 DB 비밀번호는 입력하거나 공유하지 않습니다.
5. 앱에서 이메일로 로그인합니다. 받은 메일의 링크를 해당 기기에서 엽니다. 메일 발송 제한이 있으면 잠시 후 다시 시도하며, 여러 사용자에게 서비스하려면 Supabase의 SMTP 설정이 추가로 필요합니다.
6. **각 기기의 원본을 먼저 JSON으로 보관한 후**, 기록이 가장 많이 남아 있는 기기에서 ‘이 기기 기록으로 온라인 저장 시작’을 누릅니다. 기록이 이미 온라인에 있다면 최신 날짜와 내용을 비교합니다. 온라인 기록 불러오기는 전체 사본을 바꾸며 두 사본을 자동으로 합치지 않습니다.
7. iPad·휴대폰에서도 같은 URL·공개 키와 **같은 이메일**로 로그인합니다. 이 기기에 별도로 입력한 최신 내용이 있다면 아래 **기록 복구**에서 원본을 먼저 확인합니다. 이 기기에만 있는 기록이 없음을 확인했을 때 온라인 사본으로 바꾸는 확인란을 선택하고 **온라인 기록 불러오기**를 누릅니다.

Vercel 환경변수로 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`를 설정하고 다시 배포하면 각 기기에서 URL·공개 키를 입력하는 4번 단계는 생략됩니다. `.env.example`을 참고하세요. 이 두 값은 브라우저에 공개되는 설정이며, 비밀 키를 넣으면 안 됩니다.

## 기록 보존과 동시 사용

- 로그인 전 원본 데이터는 기존 V1 저장 키에 그대로 두고, 온라인 연결 후의 기기 캐시는 계정별로 분리합니다. 로그인하지 않은 화면에서는 이전 기기 기록이 보이며 같은 계정으로 다시 로그인하면 해당 계정의 저장 기록을 읽습니다.
- 모든 자료·강의 목록·학습/복습/작업 기록·회독 위치·할 일·일정·목표를 하나의 문서로 저장합니다. 취소·삭제와 실제 학습시간 수정도 같은 방식으로 반영합니다.
- 변경은 약 0.7초 후 서버에 저장합니다. 다른 기기의 변경은 화면 복귀·온라인 재연결·약 30초 주기로 확인하며 **지금 동기화**로 즉시 확인할 수도 있습니다. 서버 저장 응답을 받기 전에는 온라인 저장 완료라고 표시하지 않습니다.
- 네트워크 오류 시 기기 캐시에 변경을 보존하고 재연결 시 다시 확인합니다. 저장 공간 부족·읽을 수 없는 데이터는 경고하고 원본을 덮어쓰지 않습니다.
- 두 기기에서 각각 수정하면 자동 병합이나 최종 수정 우선 덮어쓰기를 하지 않습니다. 양쪽 기록을 확인한 후 사용할 사본을 직접 선택합니다. 교체 전 양쪽 사본을 해당 기기에 백업하며 최근 4개를 내려받을 수 있습니다. 백업을 기기에 저장하지 못하면 교체도 진행하지 않습니다.
- 로그아웃해도 계정별 기기 캐시는 삭제하지 않습니다. 공용 기기 사용은 피하고, 사용했다면 로그아웃 후 브라우저 사이트 데이터를 삭제합니다.

## 로그인 후 휴대폰의 최근 기록이 보이지 않을 때

1. 기록을 입력했던 **같은 브라우저·같은 사이트 주소**에서 온라인 저장 설정을 엽니다. 사이트 데이터를 삭제하거나 다른 사본으로 다시 교체하지 않습니다.
2. **기록 복구 · 로그인 전 원본 및 교체 전 백업**을 펼칩니다. **로그인 전 이 브라우저의 원본 기록**과 **온라인 기록을 불러오기 전 이 기기 기록**을 각각 JSON으로 내려받습니다. 원본 JSON은 읽거나 변환하지 않은 저장 내용 그대로 내려받을 수 있습니다.
3. 최근 실제 활동일·학습 이력·과업 작업·할 일·최근 학습 기록을 확인합니다. 사본 저장 시각과 실제 활동일은 별도로 표시하며 계획된 목표일·일정일로 최신 학습을 추정하지 않습니다.
4. 해당 사본의 **이 사본을 복구 초안으로 열기**를 누릅니다. 먼저 현재 계정의 보이는 기록을 백업한 다음 사본을 이 기기에만 엽니다. 기기 저장에 실패하면 복구를 중단하고 이전 화면을 유지합니다.
5. 설정 창을 닫고 HOME과 상세 화면에서 누락됐던 내용이 있는지 확인합니다. 상단은 **복구 초안 · 온라인 반영 전**이며, 새로고침·화면 복귀·자동 확인·초안 편집 후에도 서버로 자동 업로드하지 않습니다.

온라인 사본과 복구 초안은 자동 병합하지 않습니다. 양쪽 JSON을 보관한 뒤 어느 사본에 최신 내용이 있는지 확인해야 합니다. 복구 초안을 온라인에 반영하는 명시적 교체도 온라인 문서 전체를 교체하므로 다른 기기에만 있는 내용을 먼저 확인합니다. 교체 전 서버 사본도 백업합니다. 로그인 전 원본이 기존 계정 캐시와 다른 경우, 다음 로그인에서도 자동으로 숨기거나 덮어쓰지 않고 기록 확인을 요구합니다. 복구 화면은 현재 계정의 백업과 로그인 전 기기 원본만 보여주며 다른 계정 캐시는 열거하지 않습니다.

저장소가 삭제됐거나 원래 사용했던 브라우저·사이트 주소와 다르면 사본을 찾을 수 없을 수 있습니다. 복구 도구가 제공된 것만으로 실제 사용자 기록이 복원됐다고 보장하지 않으며, 사본 내용을 확인해야 합니다.

## 휴대폰에서 로그인 메일 요청이 실패할 때

Android Chrome에서도 같은 이메일 로그인 방식을 사용합니다. PC·iPad에서 로그인했다고 휴대폰 로그인을 차단하지 않습니다. 인증 메일의 재요청 간격과 발송 한도는 여러 기기의 요청에도 적용되므로 연속 요청 시 제한될 수 있습니다.

### 메일 없이 기존 계정에 비밀번호로 로그인

1. 이미 로그인된 PC·iPad에서 앱을 새로고침하고 오른쪽 위 온라인 저장 상태를 누릅니다.
2. **비밀번호 설정·변경**을 펼치고 새 비밀번호와 확인 입력에 같은 값을 넣은 후 **비밀번호 저장**을 누릅니다. 8자 이상이며 프로젝트에 설정한 비밀번호 정책도 충족해야 합니다.
3. 휴대폰에서도 앱을 새로고침하고 온라인 저장 설정을 연 뒤 **비밀번호 로그인**을 선택합니다.
4. **기존과 같은 이메일**과 방금 정한 비밀번호를 입력하고 **비밀번호로 로그인**을 누릅니다. 이 과정에서는 인증 메일을 요청하지 않습니다.
5. 기록 선택이 나오면 **온라인 기록 불러오기**를 선택하고 온라인 저장 완료와 기존 기록을 확인합니다.

현재 로그인한 Supabase Auth 사용자의 비밀번호만 설정하므로 사용자 ID·기존 계정·학습 문서는 바꾸지 않습니다. 비밀번호는 학습 데이터나 앱의 브라우저 캐시에 저장하지 않고 Supabase Auth에서 관리합니다. 설정 시 최근 로그인 확인이 필요한 보안 정책이 적용된 프로젝트는 메일 한도가 회복된 후 재로그인이 필요할 수 있습니다. 비밀번호를 잊었다면 로그인 중인 다른 기기에서 다시 설정할 수 있으며, 모든 기기에서 로그아웃했다면 메일 로그인을 통해 복구해야 합니다.

앱은 메일 발송 한도(`over_email_send_rate_limit`), 요청 제한(`over_request_rate_limit`), 기본 메일 서비스의 수신자 제한(`email_address_not_authorized`), 잘못된 연결 키와 네트워크 오류를 구분해서 표시합니다. 응답에 구체적 재요청 시간이 있으면 그 시간을 사용하고, 메일 요청 성공 후에는 60초 동안 버튼과 Enter 재요청을 막습니다. 이 60초 대기는 서버의 시간별 발송 한도를 해제하는 기능은 아닙니다. 오류 코드만으로 기기의 운영체제가 원인이라고 판단하지 않습니다.

오류가 계속되면 화면의 오류 코드 또는 HTTP 상태를 확인한 후 Supabase의 Auth 로그·Rate Limits·SMTP 설정에서 원인을 확인합니다. 원본 오류 메시지의 이메일·인증 링크·키는 화면에 그대로 노출하지 않습니다.

## 접근 제어와 검증 범위

`dashboard_snapshots`는 RLS로 로그인한 본인의 행만 조회합니다. 익명 접근과 클라이언트의 테이블 직접 쓰기를 금지하고, `save_dashboard` 함수는 `auth.uid()`와 기대 버전을 검증한 후에만 저장합니다. 공개 키만 알아도 다른 사람의 기록을 조회하거나 수정할 수 없습니다.

자동 테스트는 최초 기록 연결, 두 기기 충돌, 버전 경쟁, 오프라인 복원, 업로드 도중 추가 편집, 로그아웃·계정/프로젝트 분리, 수정·삭제 보존, 손상된 캐시와 저장 실패를 검증합니다. 별도 PostgreSQL 실행 환경에서 SQL의 생성·수정·충돌·RLS·익명 접근 차단도 확인했습니다. 브라우저 테스트는 Supabase API를 모의하여 두 기기의 화면 연동을 확인합니다. 실제 Supabase 프로젝트·메일 발송·Vercel 환경변수 연결은 사용자 계정 설정 후 최종 확인해야 합니다.
